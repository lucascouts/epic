# Self-Review Checklist

Shared checklist applied before writing each phase artifact to disk.

## Inline Review (all scales)

Before writing each phase artifact to disk, silently ask yourself:

1. **Inputs covered?** Every user input has a validation rule or explicit "no validation" decision
2. **Ownership clear?** Every entity has clear ownership semantics
3. **Error paths?** Every happy path has a corresponding error/failure path
4. **State transitions?** For every "user does X", what happens if already in state X?
5. **Consistency?** Every entity in story.md appears in design.md, every requirement in tasks.md
6. **Scope leaks?** Nothing added that the user didn't request or confirm
7. **Parameters concrete?** Every numeric limit, threshold, page size, timeout, or retry count referenced in requirements has an explicit value — either in the requirement itself or in Constraints
8. **Open decisions resolved?** Every "or" / "alternatively" / "either X or Y" in design.md is resolved to a single approach in tasks.md — tasks must not inherit ambiguity from design
9. **Interface contracts satisfied?** (Phase 2+3) Every data boundary between components has matching shapes on both sides. When component A produces output consumed by component B, the data structure A sends must contain every field B expects. This applies to any producer→consumer relationship: handler→template/view, API→client, service→controller, parent→child component, event emitter→listener. For each interface defined in design.md, trace the data shape from producer to consumer and verify completeness.
10. **Error propagation complete?** (Phase 3) Every operation in a ToDo field that can fail must have explicit error handling **OR** a documented reason why the framework handles it. In languages/frameworks where input parsing is automatic (Django, Spring Boot, FastAPI, Express with middleware), framework-handled errors are acceptable without explicit mention. In languages/frameworks where it's manual (Go net/http, Rust actix-web, plain Node.js), the ToDo must say "parse input **and handle error**". This applies to ALL function calls that return errors — not just store/service methods but also stdlib functions like form parsing, type conversions, and file operations. The rule: **no silent failure at system boundaries**. When writing ToDo fields, use "call X and handle error" rather than just "call X".
11. **Testing strategy covered?** (Phase 3 only) Every testing level defined in design.md's Testing Strategy has at least one corresponding task with a Tests field. If a level is missing, flag it — do not silently drop it.
12. **Literal fidelity?** Re-read each requirement as a checklist of **behaviors**, not a single action. "Do A with B displaying C" is three checks: (1) does A, (2) with B, (3) displaying C. Every qualifier, prepositional phrase, and conjunction in the requirement is a separate verification point. If a task ToDo implements the main verb but drops a qualifier (e.g., "redirect to login" but the requirement says "redirect to login **with a success message**"), the task is incomplete.
13. **Interface consumers exist?** (Phase 2) For every function, class, or component listed in design.md's Components & Interfaces section, verify at least one of: (a) it is consumed by another component in the design's described flows, (b) it is explicitly referenced by a task as a dependency, (c) it is marked as "prepared for Task N" with a forward reference. An interface with none of these is either orphaned (design/implementation mismatch) or speculative (designed for a future that may not come). Flag it.
14. **Hostile half covered?** (Phase 3) For every requirement asserting that two things are the SAME or DIFFERENT (identity, uniqueness, deduplication, distinguishability), ask: which fixture would make this rule fire wrongly — collapsing two distinct things into one, or splitting one thing into two — and is that fixture in the suite? Every such requirement has a converse, and a fix that satisfies one by violating the other stays green against a suite covering only the benign half, so a Tests field naming only the case where the rule plainly holds is a **half-covered rule** — flag it (see `agents/test-advisor.md`, *Hostile-half rule*). **Then ask the same of every value the fix DERIVES** — a rendered string, a resolved name, a computed key: *can a THIRD element collide with it?* A requirement can only name what it forbids, never a spelling the fix invented, so a suite authored from the requirement alone can cover the hostile half correctly and still leave the new mechanism untested — a uniqueness check written over a pair, holding at two and breaking at three.

15. **Pointers re-read, not just re-pointed?** Every citation an artifact carries — `path/file.md:120`, or a bare `:120` whose target file lives only in the surrounding prose — is a claim about **content**, and the content slides out from under it whenever anything above it is edited. So a pointer is verified by **opening the target and reading it**, never by checking that the number falls inside the file. Two rules follow, and the second is what makes the first checkable. **(a) Re-point AND re-quote.** A repair that corrects the line number and leaves the quoted text alone leaves the citation wrong *and looking repaired* — the worst of the three states. **(b) Quote the anchor when you write it.** Name the field, heading or sentence the range lands on, so the next reader can tell a moved pointer from a wrong one without opening anything. This is deliberately **not** a mechanical check, and the measurement that decided so is worth stating because it is counter-intuitive: swept project-wide over the epic's own artifacts (story `006-git-aware-lifecycle`, sub-task 11.4), a line-number bound-check finds **0 violations across 51 pointers — and only 32 of those 51 were decidable at all**, the other 19 naming a file the check cannot resolve. Zero violations there is the absence of a subject, not a green. It would also have caught **none of the four times this defect recurred** — three were bare `:line` pointers it cannot resolve at all, and the fourth was in range and wrong. The recurring defect is *in-range-with-wrong-content*, which no line-number check can see.

16. **Both ends of the wire, not just one?** (Phase 3) A script, module or endpoint is finished when something *calls* it — an implementation with no consumer is a contract built at one end. Ask it in **both directions**, because they fail differently and only one of them is ever noticed: **(a)** does every executable this story ships have a caller on the **production** surface — the docs, skills, hooks, agents, manifests and other scripts that make up the shipped path — and not merely in its own test file? **(b)** does every path a consumer *cites* actually resolve to a file that exists? An **invocation** is what counts: a comment naming the basename, a prose reference and a changelog line are mentions, and a mention has never executed anything. This is deliberately **not** a mechanical check, and the measurement is the reason: swept project-wide (story `006-git-aware-lifecycle`, sub-task 12.3) it finds **0 violations across 25 executables and 23 cited paths**, so there is no population to set a severity from; legitimate zero-caller exemptions exist — **PATH entry points, and those only**, the "documented hand-run tool" class having been withdrawn at sub-task 13.2 when the two scripts held up as examples turned out to have three and one invocation respectively, both predating the sweep that called them orphans — so an unconditional error would need an allowlist — a place to write the answer, not a way to compute it; and the check's own **three** derived values — **the surface list**, **the invocation matcher** and **the path regex** — each returned a wrong answer, the first two during that sweep and the third found at 13.2 inside the correction the first one produced. The surface list is the sharpest, because it is not derivable from the population it sweeps: omit one directory and a wired script is reported as an orphan. The matcher is the subtlest: it can be *narrower than the rule it implements* — recognising `${PLUGIN_ROOT}/scripts/…` and `./scripts/…` while dropping the bare-relative `bash scripts/<name>` the rule's own wording admits — so the file is read, the invocations are there, and the report says orphan anyway. What makes this catchable by reading is that the symptom is legible at the *consumer* — a reference file that describes a behaviour in prose where a sibling passage invokes a script is the tell.

17. **Did this edit invalidate a number or a pointer it did not touch?** (all phases) The defect items 15 and 16 chase from the outside, seen from the inside: a repair that adds a line, a case or a paragraph **falsifies the counts and coordinates written about the thing it repaired** — and the falsification ships in the same commit as the fix, looking freshly verified. Story `006-git-aware-lifecycle` produced **four in one group**: a gate's `307/307` was true until the same commit added seven test cases; a register's `design.md:94` was true until the same sub-task's sync added a history line above it; the sub-task written to correct that pointer rewrote the entry **in place** and moved its own cited coordinate one line; and the sub-task that retires this question re-displaced all of them with its own version sync. So before finishing an edit, ask what the edit *displaced*: a frontmatter line moves every body line, a new test moves every count, a rewritten field moves everything below it inside its own file. **The durable defence is not a number that is right today but a citation that cannot go stale** — quote the anchor (item 15b), and state a count as a dated reading with the command that re-derives it, never as a property.
    - **A quoted anchor is immune to displacement but not to duplication, and that is the trap the fourth instance sprang.** The same sync that moved the coordinates also *quoted the anchor phrase verbatim* in its history line, taking the phrase's occurrence count from one to two and spending the uniqueness the anchor was chosen for. The edit most likely to duplicate an anchor is the one writing prose *about* the sentence it anchors — a sync note, a changelog line, a deviation record. So when you write an anchor, measure its uniqueness; and when you write *about* an anchored sentence, **describe it rather than quote it**.
    - **Not mechanical, and the reason is specific rather than general — measured at sub-task 13.4 before this item was written.** The precise check is easy to describe: when an artifact's frontmatter grows by *N* lines, shift every pointer into its body by *N*. It needs one thing this project cannot supply — the artifact's **previous** state. `.epic/` is gitignored (`git ls-files .epic/` returns **0**), so no commit ever touches these files and there is no before-state to diff against. Without it a checker can only warn *"this pointer targets an artifact whose frontmatter may have moved"*, which is true of every such pointer after every sync and discriminates nothing — item 15's *in-range-with-wrong-content* verdict arriving by a second road.
    - **The population does not carry a project-wide rule either.** Swept over all **7** story directories (32 artifact files: `story.md`, `design.md`, `tasks.md`, `.draft/*.yaml`; `.epic/archive/` does not exist): **95** Form A pointers, of which only **18** target a sibling story artifact and are therefore breakable this way — and **13 of the 18 sit in story 006 alone**. All 18 resolve in range, including the seven spellings of `design.md:94`, one of which pointed at a **blank line**. A rule whose subject is 72% one story's own habit is that story's discipline, not the project's — 10.3's severity-by-measurement standard, returning **NO** for the third consecutive time after 11.4's pointer check and 12.3's orphan check. Retired, not deferred: no follow-up group is owed.

If a trivial gap is found (formatting, naming), fix it silently. If a **substantive gap** is found (missing test level, orphan requirement, unaddressed security consideration), present it to the user: "During self-review I noticed: [gap]. Add a task or move to Out of Scope?"
